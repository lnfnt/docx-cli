# SPEC — docx-cli v0.9.0

**Статус:** реализовано и принято (v0.9.0, акт приёмки 24.10.2026).
**Принципы:** fail-closed, production-grade, без костылей, машинный контракт для ИИ-агентов, полная документация без взгляда в код.

## 1. Назначение

`docx-cli` — локальный CLI/Python-пакет для детерминированной генерации русскоязычных юридических документов в формате .docx (процессуальные документы, ответы в госорганы, письма, правовые анализы).

**Целевая аудитория:** практикующие юристы и ИИ-агенты, вызывающие генерацию из автоматизированных пайплайнов.

**Проблема, которую решает:** генерация документов обычно остаётся одноразовыми скриптами с дублированной логикой. Каждый новый документ = новый скрипт с копипастой. Документы меняются — скрипты разъезжаются со стандартом.

## 2. Что НЕ входит (границы)

- НЕ валидирует юридическое содержание и не проверяет нормы права (это задача правоприменителя).
- НЕ парсит PDF/сканы.
- НЕ рендерит в PDF (может проверить наличие LibreOffice через doctor, но не конвертирует).
- НЕ придумывает факты: вход — только то, что дал вызывающий. Пробелы — плейсхолдеры `[УКАЗАТЬ ...]`, не тишина.
- НЕ редактирует существующие .docx (только генерация с нуля; произвольное редактирование — вне объёма).

## 3. Стандарт оформления (единственный, зашит по умолчанию)

Источник истины: внутренний стандарт оформления (ГОСТ-юридический дефолт):

| Параметр | Значение по умолчанию |
|---|---|
| Бумага | A4 (не Letter) |
| Поля | L=3.0, R=1.5, T=2.0, B=2.0 см |
| Шрифт | Times New Roman, 12 pt (заголовки 14 pt) |
| Межстрочный | 1.5 (шапка/титул 1.15) |
| Абзацный отступ | 1.25 см |
| Выравнивание тела | justified |
| Ё | запрещена в тексте, кроме официальных реквизитов (паспорт, СНИЛС, юр-реквизиты) — валидатор предупреждает |
| Тире | только «—» или «-», en-dash «–» запрещён — валидатор исправляет/предупреждает |

Профиль документа переопределяет параметры, но дефолт один — ГОСТ-юридический.

### 3.1 Профиль `court`

Профиль `court` предназначен для процессуальных документов (арбитраж, суды общей юрисдикции, надзорные органы):

| Параметр | Значение |
|---|---|
| Шрифт | Times New Roman, **14 pt** для всего документа (шапка, заголовок, тело, списки, таблицы, подпись) |
| Межстрочный интервал | 1.0 (допустимо переопределить на 1.15 через `line_spacing`) |
| Поля | Л=3.0, П=1.5, В=2.0, Н=2.0 см |
| Абзацный отступ | 1.25 см |
| Шапка | блок с `left_indent = 7.0 см` (допустимый диапазон 6.0–8.0), выравнивание строк LEFT |
| Заголовок | CENTER, Bold, 14 pt, `space_before/after = 12 pt` |
| Маркер «ПРОШУ» | отдельный блок `pleading_marker`: CENTER, Bold, 14 pt, без абзацного отступа |
| Списки | висячий отступ: `left_indent = 1.25 см`, `first_line_indent = -0.75 см` |
| Подпись | текстовый формат (без таблицы) по умолчанию; допустим явный `format: "table"` |

## 4. Архитектура

```
docx_cli/
  __init__.py          # публичный API: build_document, DocSpec
  __main__.py          # python -m docx_cli
  cli.py               # argparse CLI: build, validate, doctor
  spec.py              # DocSpec (pydantic): профиль документа, стороны, блоки
  builder.py           # ядро генерации (python-docx), стили, блоки
  blocks.py            # типы блоков: header, title, body, table,
                       # numbered_list, signature_block, attachments_list
  validate.py          # встроенный валидатор результата (порт docx_validate.py
                       # + ГОСТ-проверки: поля, шрифт, интервал, отступ, ё, en-dash)
  errors.py            # SpecError, BuildError, ValidationError (fail-closed)
models.json example:
  см. examples/spec_example.json
```

## 5. Машинный контракт

### 5.1 CLI

```
docx-cli build <spec.json> <output.docx> [--profile gost|compact|court]
docx-cli validate <file.docx> [--json]      # exit 0=ok, 1=errors, 2=warnings only w/ --strict
docx-cli doctor                              # env: python-docx, lxml, права записи
```

Все команды выводят JSON-конверт:
```json
{"ok": true, "status": "ok", "reason": null, "parsed_at": "...", "data": {...}, "metadata": {...}}
```

### 5.2 Spec (JSON, pydantic-валидация)

```json
{
  "profile": "gost",
  "output": {"file_name": "2026.09.22.Отзыв_истца.docx", "author": "Иванов И.И."},
  "header": {"align": "right", "lines": ["В ... суд", "Истец: ..."]},
  "title": {"main": "ОТЗЫВ ИСТЦА", "subtitle": "на возражения ответчика"},
    "body": [
      {"type": "paragraph", "text": "..." , "inline_markdown": true},
      {"type": "numbered_list", "items": ["..."]},
      {"type": "table", "headers": [...], "rows": [[...]], "widths_cm": [...]},
      {"type": "pleading_marker", "text": "ПРОШУ СУД:"},
      {"type": "signature_block", "left": "Представитель", "right": "___________ /Иванов И.И./", "format": "table"},
      {"type": "attachments_list", "items": ["1. Копия ... на N л."]}
    ],

  "checks": {"no_yo": true, "no_en_dash": true, "require_norms_refs": false}
}
```

Правила spec:
- Любое нарушение схемы → SpecError, exit 1, JSON `{"ok": false, "status": "error", "reason": "spec_error: <деталь>"}`. Никаких «похожих» полей, никаких дефолтов-догадок.
- Плейсхолдеры `[УКАЗАТЬ ...]` разрешены и подсвечиваются в validate (warning `placeholder_present`), если `checks.require_norms_refs` и т.п. не запрошены жёстче.
- Если `checks.no_yo` — валидация после сборки ищет «ё» вне whitelist-реквизитов; находка → warning (не молча).

### 5.3 Валидатор (встроенный, всегда после сборки)

Проверки результата (после генерации builder сам себе валидирует файл):
1. Пакет открывается, части на месте, связи резолвятся (порт docx_validate.py).
2. Поля секции = профилю (±0.05 см).
3. Все run'ы: Times New Roman; размер тела/заголовков по профилю.
4. Межстрочный интервал тела = 1.5.
5. Абзацный отступ тела = 1.25 см.
6. Нет en-dash; при checks.no_yo — нет «ё» вне реквизитов.
7. Нумерация в numbered_list последовательная (1,2,3 без пропусков).

Результат в metadata: `{"checks": {"margins": "pass", "fonts": "pass", ...}, "warnings": [...]}`. Любая error-находка = exit 1 и файл НЕ считается готовым (builder удаляет частичный вывод).

## 6. Требования к реализации

1. Python 3.11+, зависимости: python-docx, pydantic, lxml.
2. Тесты pytest: ≥ 60, каждый ГОСТ-параметр покрыт тестом на реальном сгенерированном файле (читаем обратно docx и проверяем XML/свойства, не «на слово»).
3. Пример: `examples/spec_example.json` + golden-тест (собранный файл сравнивается по структурным признакам).
4. Документация: README.md, SPEC.md (этот файл), docs/{USAGE,ARCHITECTURE,LIMITATIONS}.md — человекочитаемо, без взгляда в код.
5. doctor проверяет: версию python, импорт пакета, наличие python-docx/lxml, права записи в cwd.

## 7. Критерии приёмки

- `docx-cli build examples/spec_example.json out.docx` → exit 0, JSON ok:true, файл открывается, валидатор все проверки pass.
- Обратное чтение out.docx подтверждает: поля/шрифт/интервалы/отступ — по разделу 3.
- Тест-сьют зелёный; fabricating-тестов нет (все значения проверяются чтением файла).
- Старые одноразовые скрипты не трогаем — они выпадают естественно после принятия продукта.
